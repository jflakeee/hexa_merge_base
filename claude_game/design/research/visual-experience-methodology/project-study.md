# 현재 게임의 관찰과 우선 실험

관찰 자료: 기존 2026-10-05 QA 스크린샷 2장을 직접 열어 확인했다. 이 이미지는 현재 운영 상태를 새로 캡처한 것이 아니며, 정지 장면 관찰과 실시간 동작 검증을 구별한다.

## 1. 관찰 근거

- [기존 데스크톱 화면](../../qa/2026-10-05/presentation/07-desktop.png): 중앙의 세로 게임 영역, 반복되는 벽·바닥 패턴, 작은 캐릭터, 아래 설정 패널이 보인다. 이 장면은 설정 탭이 열린 상태다.
- [기존 피격 화면](../../qa/2026-10-05/presentation/03-hit.png): 상단 HP 61 표시, 두 색으로 보이는 체력 바, 원형 보라색 영역, 밝게 표현된 피격 대상이 보인다. 이 한 장으로 원의 판정 의미나 효과 타이밍을 확정할 수 없다.
- [presentation.js](../../../src/systems/presentation.js): 게임 motion 설정과 OS reduced-motion 조건을 확인한다. 보상 비행은 동시 5개 제한과 420ms 애니메이션, 체력 이력은 지연 처리, 피격 섬광은 65ms 복원 예약이 있다. 이 수치가 최적이라는 증거는 아니다.
- [arenaLayout.js](../../../src/systems/arenaLayout.js): 화면 크기와 encounter에 따라 전투 범위·보스 위치/크기를 계산한다. 여러 화면 크기의 실제 표시 결과는 이번에 실행 검증하지 않았다.

## 2. E01 — 배경과 캐릭터 분리 비교

**관찰:** 데스크톱 캡처의 플레이 영역에는 반복되는 벽돌 선과 작은 바닥 장식이 넓게 분포한다.

**가설:** 캐릭터 주변 바닥 대비를 줄이면 작은 캐릭터와 드롭 위치를 찾기 쉬워질 수 있다. 현재 화면이 사용성 기준을 실패했다는 판정은 아니다.

**실험:** 현재 배경, 바닥 선 완화, 캐릭터 외곽 강화의 세 조건을 동일 장면에서 비교한다. 배경 전체를 검게 만들기보다 플레이 영역과 비플레이 영역을 나눠 조정한다.

**평가:** 캐릭터/보상 찾기 과업, 역할 구분, 분위기 선호, 움직일 때 경계 떨림. 정지 이미지와 실제 이동 모두 확인한다.

## 3. E02 — 체력 이력과 현재 값의 구분

**관찰:** 피격 캡처에서 현재 HP 숫자와 서로 다른 색의 바가 함께 보인다. 코드는 이력 바를 잠시 유지한 뒤 줄인다.

**가설:** 처음 보는 사용자는 길게 남은 바를 현재 체력으로 오해할 수 있다. 코드에 이력 의도가 존재한다는 사실과 사용자가 이해하는지는 별개다.

**실험:** 현재 표현과 이력의 채도·두께·구획을 구분한 표현을 비교한다. 즉시 값은 항상 동일하게 유지한다. 처음에는 이력 지연 시간까지 동시에 바꾸지 않는다.

**평가:** 피격 직후 현재 체력·손실량 구분, 반복 타격에서의 정보 누적, 작은 화면의 숫자 읽기. 학습 전/후를 구분한다.

## 4. E03 — 원형 효과의 의미와 판정 일치

**관찰:** 피격 캡처에 보라색 원이 보이지만 이미지 자체만으로 위험·오라·저주 중 어떤 의미인지 확인할 수 없다.

**실험 전 단계:** 실제 효과 종류와 판정 영역, 중심·반경·지속 시간을 코드/실행에서 확인한다. 확인 전에는 “위험 예고가 틀렸다”고 결론 내리지 않는다.

**실험:** 종류에 맞는 테두리·아이콘·패턴·문구를 비교한다. 위험과 버프가 원형이라는 이유만으로 같은 색/선 모양을 공유할 필요는 없다. 판정 디버그 표시를 함께 녹화하되 제품 화면에는 개발 정보를 노출하지 않는다.

**평가:** 출처·위험 여부·유효 범위의 설명, 다른 효과와 겹쳤을 때 식별, 색 이외 단서의 유지.

## 5. E04 — 감소 모드와 피격 표현의 분리

**코드 사실:** `rewardFlight`와 `deathEcho`는 motionEnabled를 확인하지만 `flashSprite` 자체에는 같은 확인이 없다. 호출부 전체와 다른 설정의 영향을 조사하지 않았으므로 전체 감소 모드 실패라고 단정하지 않는다.

**가설:** 움직임 감소와 강한 섬광 감소를 별도 요구로 정리하면 선택권과 정보 보존을 더 명확히 할 수 있다.

**실험:** 기본, 이동 효과 없음, 섬광 완화의 조건에서 피격 인식과 불편 보고를 비교한다. 섬광을 줄이면 정적 외곽·HP 변화 같은 대체 단서를 유지한다. 짧은 65ms라는 사실만으로 점멸 안전성을 판단하지 않는다. 반복 빈도·화면 면적·명암 변화도 별도 검토 대상이다.

## 6. E05 — 카메라 확대와 보상 좌표 연결

**코드 사실:** 보상 비행 시작 위치 계산에는 camera.scrollX/Y와 캔버스 크기 비율이 사용되며, 읽은 함수에서는 카메라 zoom/rotation 변환이 명시적으로 반영되지 않는다.

**가설:** 향후 카메라 줌·회전 연출을 결합하면 화면의 획득 위치와 비행 시작점이 어긋날 가능성을 확인할 필요가 있다. 현재 운영 장면에서 실제 어긋남을 재현한 것은 아니다.

**실험:** 기본 줌과 후보 줌, resize, 고 DPI, 모션 끔, 씬 종료를 비교한다. 필요하면 월드→화면 변환을 하나의 함수로 관리하는 방안을 검토한다.

**평가:** 시작/도착 위치 오차, 종료 후 남은 DOM 효과, 실제 보상 값과 표현의 일치. 좌표를 맞추기 위해 게임 상태 지급 시점을 애니메이션 완료에 종속시키지 않는다.

## 7. 실행 순서와 범위

우선 E03으로 효과 의미를 확인하고 E01/E02의 읽기 개선을 비교한다. E04는 모션 정책을 정리하는 작업으로 병행하고, E05는 카메라 확대를 추가하기 전에 확인한다. 그 후 팔레트·윤곽·하프톤 같은 스타일 후보를 선택한다.

현재 상태는 다섯 실험 모두 **설계 완료 / 구현·실행 검증 전**이다. 이전 QA 성공 결과를 이 실험의 통과 증거로 재사용하지 않는다.
