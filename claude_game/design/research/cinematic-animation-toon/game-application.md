# ClaudeGame 적용 설계와 검증 기준

상태: 연구 및 설계 제안. 아래 수치·콘티·구조는 구현/실행 검증 전이며 확정 성능 예산이 아니다.

## 1. 우선순위

| 순서 | 조합 | 목적 | 비용/조건 |
|---|---|---|---|
| 1 | E03 그래픽 매치 + E06 L 컷 | 보상→장비 화면의 관계와 연속감 | 낮음~중간. 대응하는 아이콘·오디오 수명 관리. |
| 2 | C04 횡이동 + A14 시차 + F04 여백 | 보스 등장 공간감 | 중간. 배경 레이어와 화면 경계 처리. |
| 3 | N01 명암 + N12 팔레트 + N05 림 | 보스 실루엣과 위협감 | 중간. 아트 제작이 핵심. |
| 4 | E05 J 컷 + C09 약한 줌 + E01 컷 | 짧은 보스 소개 | 중간. 연출 소유권·스킵·전투 복원 필요. |
| 5 | N10 포즈 유지 + 스미어 | 캐릭터별 움직임 성격 | 중간. 애니메이션 타이밍과 판정 분리. |
| 연구용 | C10 돌리 줌, N06 해칭, C07 오빗 | 강한 스타일 실험 | 높음. 2D 근사 또는 신규 에셋/3D 구조 필요. |

보통 전투 중에는 F04 구도, 제한된 C08 추적, 읽기 쉬운 N01/N12를 우선한다. 큰 회전·랙 포커스·화면 전환은 공격 회피 판단과 충돌할 수 있어 등장·이동·결과 장면에서 먼저 시험한다.

## 2. Phaser 구현 대응

| 표현 | 구현 수단 후보 | 반드시 확인할 점 |
|---|---|---|
| 위치 이동/확대 | Camera pan/zoom, tween | `pan`은 월드를 바라보는 중심을 스크롤하며 화면 안의 viewport 사각형 위치를 옮기는 기능과 다르다. 겹치는 연출이 같은 카메라 값을 동시에 쓰지 않도록 한다. |
| 따라가기 | startFollow, deadzone, 별도 look-ahead 목표 | look-ahead는 이동 노이즈를 증폭할 수 있음. 정지/방향 전환에서 흔들림 확인. |
| 페이드/컷 | Camera fade 이벤트, Scene 전환 | 연출 완료·자산 준비·상태 변경을 분리해 중복 실행 방지. |
| 와이프/디졸브 | 마스크, 두 화면/레이어, RenderTexture | 재사용 가능한 버퍼 수 제한. 단순 opacity 혼합과 선형 광량 혼합은 결과가 다름. |
| 포커스 근사 | 월드 레이어별 FX/사전 흐림 이미지 | 실제 깊이 기반 DOF 아님. HUD는 별도 유지. |
| 시차 | 배경 레이어별 scroll factor 또는 자체 이동 | 줌 중 빈 가장자리, 텍스처 반복 이음새, 픽셀 떨림 확인. |
| 툰/해칭 | 사전 제작 에셋 우선, 필요 시 custom pipeline | Phaser FX는 WebGL 의존 기능이 있음. Canvas fallback 표현을 따로 결정. |
| 2D 광원 | normal map을 사용하는 Light 파이프라인 또는 그림 | 장식 PointLight와 다른 물체에 작용하는 조명 구별. |

카메라 기능은 [Phaser Camera 3.90 API](https://docs.phaser.io/api-documentation/3.90.0/class/cameras-scene2d-camera), 효과의 지원 범위는 [Phaser FX 공식 개요](https://docs.phaser.io/phaser/concepts/fx)를 참조한다. follow의 선행 시점·dead zone·damping 설계 참고는 [Unity Cinemachine Position Composer](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/CinemachinePositionComposer.html)이며 그 기능이 Phaser에 동일하게 내장되어 있다는 뜻은 아니다.

## 3. 보스 등장 콘티 — 총 1.2초의 최초 실험안

| 구간 | 화면 | 소리/게임 상태 | 사용 기법 |
|---|---|---|---|
| 0~0.15초 | 현재 구도 유지, 보스 방향을 밝힘 | 낮은 등장음 시작. 연출 시작 상태를 한 번만 등록 | J 컷, 동기 있는 조명 |
| 0.15~0.55초 | 카메라 중심을 보스 쪽으로 약하게 이동, 배경 2~3층 시차 | 공격 판정은 일관된 연출 정책에 따라 대기 | 트럭 근사, 시차 |
| 0.55~0.85초 | 보스 핵심 포즈, 약 1.04배 확대를 초기 실험값으로 사용 | 핵심 음향, 이름 표시 | 줌, 포즈 유지, 림 |
| 0.85~1.20초 | 플레이 구도로 복귀 | 잔향 유지, 입력/HUD 복원 후 전투 준비 완료 | L 컷, 연속성 |

반복 플레이에서는 생략 또는 더 짧은 버전을 제공한다. 모션 감소 모드에서는 카메라 이동/확대를 생략하고 안정된 구도·이름·소리로 동일 정보를 전달한다. 입력이 필요한 실제 전투가 이미 시작된 상태라면 이 콘티를 그대로 끼워 넣지 않는다.

## 4. 연출 상태 관리 제안

```text
요청 → 준비 → 재생 → 정상 종료/스킵/씬 종료 → 공통 정리
                           └──────────────→ 동일한 다음 게임 상태
```

연출 관리자는 카메라·입력·시간 배율·오디오의 임시 변경을 소유한다. 시작 전 값을 보관하고 끝날 때 복원하되, 종료한 옛 연출이 새 연출의 값을 덮지 않도록 소유 토큰을 확인한다. 단순히 마지막에 `timeScale=1`을 쓰면 기존 일시 정지 상태를 깨뜨릴 수 있다.

장면 전환은 취소/중복 요청에 안전해야 한다. 핵심 보상·퀘스트·보스 상태는 영상 타이밍에 매달지 않고 게임 상태 처리에서 정확히 한 번 확정한다. 스킵으로 효과가 생략되어도 결과는 같아야 한다. 카메라 연출은 한 조정자가 위치/줌을 합성하고, 작은 충격 오프셋을 별도 계층에서 더하는 구성을 검토한다.

캐릭터를 온 투스로 보이게 할 때는 포즈 선택 시간을 양자화한다. 렌더러·입력·충돌 검사를 함께 낮은 FPS로 제한하지 않는다. 저속 포즈와 빠른 이동이 충돌하면 발 미끄러짐, 방향 전환, 카메라 추적을 따로 조정한다.

## 5. 구현 후 시각 검증 계획

아직 수행하지 않은 검증 계획이다. 문서 검사를 실제 렌더링 통과로 표시하지 않는다.

- **촬영 조건:** 동일 장면·동일 난수 시드·동일 뷰포트로 원본과 후보를 녹화한다. 정상 속도와 프레임 단위 확인을 병행한다.
- **전환:** 첫/마지막 프레임, 중간 컷, 스킵 직후를 캡처한다. 검은 빈 프레임, 중복 HUD, 위치 점프, 전환 뒤 입력 불능이 없어야 한다.
- **카메라:** 캐릭터/적/공격 예고가 화면 밖으로 사라지지 않는지 검사한다. 재생 중 resize·연속 요청·씬 종료를 실행한다.
- **툰:** 축소/확대·저해상도·고 DPI에서 선 두께, 해칭 모아레, 명암 경계 깜박임을 확인한다. 움직이는 패턴이 표면에 붙어 있는지 검사한다.
- **게임 상태:** 정상 종료와 스킵의 보상·체력·다음 상태가 같아야 한다. 시간 배율과 카메라 값, 이벤트 리스너, 오디오 수명이 복원되어야 한다.
- **성능:** 목표 기기에서 효과 전/중/후 프레임 시간 분포와 메모리 증가를 측정한다. 60fps 목표라면 프레임 전체 16.7ms 내에서 기존 전투와 함께 평가한다. 특정 효과만 16.7ms를 쓰도록 허용하는 뜻이 아니다.
- **모션 감소:** 이동·회전·줌을 꺼도 등장/피격/보상 정보가 남아야 한다. 색과 소리만으로 정보를 독점하지 않도록 텍스트·형태도 유지한다.

기존 30종의 검증 결과는 기존 구현에 대한 증거이며 이 새 콘티나 셰이더가 통과했다는 증거로 재사용하지 않는다.
