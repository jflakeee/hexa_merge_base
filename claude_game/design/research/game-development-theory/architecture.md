# 기술 구조·시간·AI·성능 이론

## 1. 게임 루프와 시간의 소유권

게임 루프는 입력을 받고 상태를 갱신하고 화면을 그리는 반복이다. 엔진이 이미 루프를 관리하면 게임 코드에서 경쟁하는 별도 루프를 만들기보다 해당 수명주기에 맞춘다. [Game Programming Patterns: Game Loop](https://gameprogrammingpatterns.com/game-loop.html).

가변 delta를 그대로 모든 계산에 넣으면 긴 프레임에서 물리와 충돌이 불안정해질 수 있다. 고정 시간 간격은 시뮬레이션을 일정한 간격으로 진행하고 필요하면 렌더링 보간과 분리한다. 밀린 계산이 프레임을 더 늦추는 악순환에는 최대 따라잡기 범위와 처리 정책이 필요하다. [Glenn Fiedler: Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/).

현재 게임에 대한 검토 기준:

| 시간 종류 | 목적 | 분리해야 하는 이유 |
|---|---|---|
| 벽시계 | 저장 시각, 현실 시간 경과 | 탭 정지·기기 시각 변경과 관계됨 |
| 시뮬레이션 시간 | 전투·쿨다운·이동 | 일시 정지와 시간 배율 정책의 대상 |
| 연출 시간 | UI, 카메라, 잔상 | 전투 정지 중에도 일부 표시가 필요할 수 있음 |
| 애니메이션 포즈 시간 | 그림 갱신 주기 | 낮은 포즈 갱신률을 입력 지연으로 만들지 않기 |

고정 timestep만으로 브라우저·플랫폼 간 결정론이 자동 확보되지는 않는다. 난수, 입력 순서, 부동소수 계산, 외부 시간까지 검토해야 한다. 방치 게임의 장시간 진행은 수백만 틱을 무조건 재생하기보다 해당 규칙에서 집계 가능한 부분과 순차 처리가 필요한 부분을 구분한다.

코드 관찰: `advanceIdleProgress`는 경계 초과 시 거리를 0으로 만들고 스테이지를 한 번 증가시킨다. 큰 delta에서 여러 구간을 넘거나 남은 거리를 보존해야 하는 요구가 있다면 이 정책을 점검할 필요가 있다. 실제 호출부의 delta 제한까지 확인한 결함 판정은 아니다. [idleCombat.js](../../../src/systems/idleCombat.js).

## 2. 상태 머신과 전이 불변식

FSM은 현재 상태와 입력에 따라 허용된 다음 상태를 정한다. State 패턴은 이를 코드로 조직하는 한 방법이며 둘을 완전히 같은 개념으로 보지는 않는다. 중첩·병렬 상태가 많으면 단일 거대 상태표가 복잡해질 수 있다. [Bob Nystrom 저자 원문](https://github.com/munificent/game-programming-patterns/blob/master/book/state.markdown).

프로젝트 설계 예:

```text
방치 → 전투 준비 → 전투 → 결과 확정 → 결과 표시 → 방치
                     └→ 탈출/패배 ────┘
```

UI 창이 열린 상태와 전투 상태는 독립될 수 있으므로 모든 조합을 하나의 enum에 섞지 않는다. 각 상태에는 진입 조건, 허용 입력, 종료 처리, 취소 정책을 명시한다.

중요한 불변식 예시는 “같은 세션의 보상은 한 번만 반영”, “이미 종료한 전투에 피해를 추가하지 않음”, “씬 종료 후 그 씬의 이벤트가 재화를 변경하지 않음”이다. 이는 새 구현을 요구하는 확정 결함 목록이 아니라 검증 기준이다. 현재 `settled` 가드는 이미 중복 정산을 막는 장치로 존재한다. [survivalCombat.js](../../../src/systems/survivalCombat.js), [combatLifecycle.js](../../../src/systems/combatLifecycle.js).

## 3. 규칙과 표시를 분리한다

권장 구조는 입력 의도를 명령으로 받고, 규칙이 상태 변경과 결과를 확정한 다음, UI·소리·효과가 결과를 표현하는 것이다. 보상 애니메이션이 끝나야 돈이 지급되는 구조는 스킵·씬 전환·오류에 취약할 수 있다.

```text
행동 요청 → 조건 검증 → 상태 변경 → 결과 이벤트 → UI/음향/연출
```

이벤트도 소유권 없이 늘리면 숨은 의존성이 생긴다. 발행 시점과 구독 해제 시점, 중복 전달 처리, 이벤트 순서를 명시한다. 작은 규칙에는 명시적 함수 호출이 더 읽기 쉬울 수 있다. ECS나 복잡한 이벤트 버스를 모든 게임의 필수 구조로 간주하지 않는다.

아이템 정의와 인스턴스 상태도 구별한다. 정의에는 이름·기본 효과·규칙을, 인스턴스에는 고유 ID·감정·소켓·획득 상태를 둔다. 데이터 테이블 변경 시 저장된 아이템과의 호환 정책을 함께 작성한다. 이는 현재 코드를 전면 재작성하라는 제안이 아니다.

## 4. 저장과 재현성

저장은 JSON을 쓸 수 있다는 사실과 의미상 유효한 게임 상태를 복원한다는 사실을 구분한다. 현재 persistence에는 기본값 병합과 일부 값 검증이 있다. 확인한 범위에서 실패 예외를 잡는 저장 경로는 있지만, 저장 실패를 플레이어가 인지하는지까지는 검증하지 않았다. [persistence.js](../../../src/state/persistence.js).

설계 점검 항목:

- 스키마 버전과 마이그레이션을 구분하고 이전 저장 표본을 보존한다.
- 손상된 값, 누락 필드, 음수·무한대, 존재하지 않는 아이템 참조의 정책을 정한다.
- 저장 직전과 정산 직후 중 어느 상태가 복원되는지 명확히 한다.
- localStorage는 이 프로젝트의 로컬 저장 수단이며 서버 권위의 경제 검증 수단으로 간주하지 않는다.
- 시드뿐 아니라 사용한 정의 버전·설정·초기 상태도 재현 기록에 포함한다.

## 5. 게임 AI는 역할을 나누어 설계한다

| 문제 | 후보 방식 | 선택 기준 |
|---|---|---|
| 단순 순차 행동 | FSM | 상태 수와 전이가 적고 명확할 때 |
| 우선순위·조건 조합 | 행동 트리 | 조건과 행동을 계층적으로 재사용할 때 |
| 여러 행동의 상대 가치 | 효용 점수 | 연속적인 상황 변화에 따라 선택할 때 |
| 위치 사이 경로 | 그래프 탐색/A* | 이동 가능 연결과 비용이 정의될 때 |
| 장면 전체 긴장 | 디렉터/스폰 규칙 | 개별 적 행동과 전투 흐름을 분리할 때 |

표는 프로젝트의 선택 가이드이며 모든 방식을 현재 게임에 추가하자는 뜻이 아니다. 효용 점수가 비슷한 행동 사이에서 매 프레임 바뀌면 불안정해질 수 있어 최소 유지 시간이나 전환 여유를 검토한다. 행동 트리도 조건·실패·실행 중 상태를 테스트해야 한다.

A*는 누적 비용과 목표까지의 추정 비용을 사용한다. 최단 경로 보장은 휴리스틱 조건과 구현의 노드 재방문 정책 등에 의존한다. 경로 탐색은 공격할 대상 선택이나 지역 충돌 회피까지 자동 해결하지 않는다. [Amit Patel: A* 설명](https://www.redblobgames.com/pathfinding/a-star/introduction.html).

## 6. 성능: 패턴을 적용하기 전에 비용을 측정한다

오브젝트 풀은 반복 생성 비용을 줄이는 선택지지만 최대 크기, 넘쳤을 때의 정책, 반환 시 상태 초기화가 필요하다. 과한 풀은 메모리 낭비가 될 수 있다. [Game Programming Patterns 저자 원문](https://raw.githubusercontent.com/munificent/game-programming-patterns/master/book/object-pool.markdown).

현재 게임에서는 피해 숫자·파티클·사운드의 순간 동시 수, UI 갱신, 전체 화면 FX를 각각 측정하는 것이 우선이다. 평균 FPS만 보지 말고 느린 프레임의 분포와 원인을 찾는다. 60fps 목표의 약 16.7ms는 프레임 전체 시간이다. CPU/GPU 시간은 일부 겹칠 수 있어 숫자를 단순 합산한 값으로 병목을 판정하지 않는다.

설계 실험 순서는 기준 장면 고정→프로파일링→병목 하나 수정→같은 조건 재측정→화질/동작 회귀 확인이다. 렌더링, 게임 로직, 메모리, 로딩을 따로 분류한다. 엔진 교체나 ECS 도입보다 과도한 갱신·중복 작업·수명 누수를 먼저 확인한다.
